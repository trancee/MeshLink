# Map: MeshLink v1

Label: `wayfinder:map`
Status: destination reached (2026-11-09)

## Destination

An approved v1 specification bundle ready to hand off as implementation tickets: `PROJECT.md` profile, `GLOSSARY.md`, ADRs for every hard decision, an implementation-independent versioned protocol spec (with conformance vectors), module + public API design, scenario/preset matrix, dependency register, documentation architecture (human + AI-optimized), and toolchain/CI plan. Prototypes are throwaway evidence only.

## Notes

- **Product:** Kotlin Multiplatform library (Android + iOS only) for BLE peer-to-peer meshes: discovery, direct and routed messages, mesh broadcast, optional delivery/read receipts, optional store-and-forward, stable at low/medium/high density. Own open protocol; MeshLink is its reference implementation. Apache-2.0.
- **Security profiles:** `unsecured` (plaintext, unauthenticated, loudly labeled), `classical`, `post-quantum`; one per mesh, mismatches rejected, never downgraded.
- **Reference scenarios → presets:** offline chat; disaster/emergency broadcast; proximity discovery; local session/multiplayer; field/industrial teams.
- **Provisional density classes** (local density, peers in radio range): low 2–10, medium 10–50, high 50–200; whole mesh ≤ ~1,000 reachable nodes. Not claims until simulated/measured (P6). Density is per node and dynamic: each node estimates its own class and adapts (routing simulation, stage C).
- **Platforms:** Android API 26+, iOS 15+; foreground guaranteed, background best-effort. Distribution: Maven Central + XCFramework via SwiftPM. Optional features ship as separate modules where a dependency/size difference exists.
- **Governance:** read `CONSTITUTION.md` (4.0.1, a MeshLink fork), `AGENTS.md`, `GLOSSARY.md`, and `KOTLIN.md` for Kotlin work, first. Every dependency needs an E3 rationale and user approval; Rust only via the Rust-approval ticket. Verify claims against primary sources; never assume — ask with options + recommendation.
- **Evidence bar:** radio decisions need real-device evidence across Android↔Android, Android↔iOS, iOS↔iOS. Device lab: 29 Android phones (`../android-devices/devices.md`); iPhones on this Mac (`xcrun devicectl list devices` for iOS 17+, `idevice_id -l` for iOS 15/16; inventory in the same devices.md). Xcode 16.4 is a hard constraint.
- **Prior art (study only, never copy code):** `../MeshLink-template` (SPEC.md, `docs/explanation/template-design-review.md` = its self-critique), `../cairn` (`docs/agents/lessons.md`, ADRs 0001/0003/0025/0038–0042, `docs/research/`).
- **Skills to consult:** grilling + domain-modeling (always for HITL); research; prototype; ble-protocol-stack, ble-throughput, android-ble*, corebluetooth, noise-protocol, kotlin-multiplatform, kotlin-gradle, skie, ubique-uniffi, robolectric, diataxis, wycheproof as relevant.
- **Research findings** live in `docs/research/` on `main`; new research lands on a `research/<slug>` branch and is merged into `main` when its ticket resolves.

## Decisions so far

- [What do existing BLE P2P meshes teach us?](issues/01-prior-art-ble-meshes.md): SIG Mesh can't be used phone-to-phone, so MeshLink needs its own dual-role protocol. Borrow managed flooding and learned next-hop routing, authenticate before relay or cache, rotate on-air identifiers, and never negotiate a downgrade.
- [What does each platform's BLE stack support in 2026?](issues/02-platform-ble-capabilities.md): GATT works everywhere; L2CAP CoC is available on both platforms (Android 29+, iOS 11+), with its port exchanged over GATT; Android↔iOS CoC is unproven, so the device-lab bake-off decides it. Discovery uses a legacy UUID-only advert plus an optional 2M extended advert. Expect about 5–6 Android links per phone; the 512 B attribute cap holds. Background is best-effort, and the BLE address is never an identity.
- [What is the most modern stable KMP toolchain in 2026?](issues/05-kmp-toolchain-2026.md): candidate baseline is Kotlin 2.4.21, AGP 9.3.x, Gradle 9.7, SKIE, SwiftPM only (CocoaPods trunk freezes 2026-12-02), Robolectric 4.17, Kover and Dokka 2.2. detekt 2 and ABI validation aren't stable yet, and Kover can't cover iOS code.
- [Is the device lab ready for cross-platform radio evidence?](issues/06-device-lab-readiness.md): all five iPhones are ready (iOS 15.8, 16.7, 17.6, 18.7, 27.0); iOS 15/16 are driven through libimobiledevice. Xcode 16.4 is a hard constraint: smoke-test the newest Kotlin and fall back to 2.2.20. No CryptoKit post-quantum crypto on iOS.
- [Which constitution amendments should MeshLink adopt?](issues/07-constitution-amendments.md): MeshLink forks the constitution as 3.1.0. T9 now requires an evidence record for hardware claims; C10 makes the protocol spec and its vectors authoritative; O8 requires a human and an agent docs layer from one source. Kotlin guidance lives in root `KOTLIN.md`, and other stack guides follow the root `<STACK>.md` pattern. The T3 iOS coverage question waits for the toolchain baseline.
- [What is the threat model, and what does each security profile guarantee?](issues/08-threat-model.md): adversaries A1–A7 are in scope; the host app is trusted. Secured profiles use authenticated links plus end-to-end encryption, open or mesh-key-gated admission, Ed25519 broadcast signatures and per-hop reassembly. Relays see only rotating routing tags; on-air identifiers rotate. Post-quantum covers confidentiality only; there is no forward secrecy for store-and-forward. Resources are always bounded and delivery is never guaranteed. Recorded in ADR 0001.
- [What handshake and crypto suite does each security profile use?](issues/09-security-profile-suites.md): a Noise suite of X25519, ChaChaPoly and SHA-256, never negotiated. Links use XX (XXpsk3 when gated, XXhfs with ML-KEM-768 for post-quantum); end-to-end uses IK with a 0-RTT first message. Post-quantum first and held messages are also sealed with HPKE/X-Wing. An Ed25519 identity certifies rotating static keys. Recorded in ADRs 0002 and 0003; first-message latency is a tracked metric.
- [Which crypto provider is approved, and is Rust part of it?](issues/10-rust-approval.md): libsodium 1.0.22 (with ML-KEM-768 and X-Wing) through our own static, symbol-hidden binding. Noise, HPKE and the certificate are in Kotlin common code. Rust is approved only as a test-only reference implementation for vectors. X-Wing is pinned to hpke-pq-05 0x647a; ≤ 1 MB per ABI. An offer to upstream HPKE to libsodium waits for approval. Recorded in ADR 0004.
- [What is the toolchain and dependency baseline?](issues/11-toolchain-baseline.md): Kotlin 2.4.21 + Gradle 9.7.1 + AGP 9.3.3 on Xcode 16.4 (no fallback needed); SKIE 0.10.16; E2 holds on detekt alpha, built-in ABI validation and Kover Beta. Targets: Android arm64/armv7/x86_64; iOS device plus simulator (radio tests on hardware only). Constitution 4.0.0: 100% coverage only where a CI tool exists, and iOS code is thin adapters. libsodium uses unmodified `-Os` upstream builds, AES never exposed. Pinned test-only Rust reference with snow#210. Dependency register checked in CI; GitHub Actions; one shared lab bundle ID on the free Apple teams. Recorded in ADR 0005.
- [What documentation architecture serves humans and AI agents?](issues/16-documentation-architecture.md): Diátaxis folders plus `docs/spec/` (BCP 14 Markdown, Wycheproof-style JSON vectors) as the authority after the Constitution; ADRs carry rationale only. Each fact has one source: protocol data in spec files, API facts (config, diagnostics, errors) in Kotlin with KDoc; reference pages and the agent JSON are generated and CI-diffed. `AGENTS.md` is the only agent file; `llms.txt` only once a site exists. Kotlin and Swift examples come from compiled tests. Dokka HTML on Pages, no site generator until release. Docs CI: lychee, markdownlint-cli2, typos (US English). Recorded in ADR 0006.
- [What public API shape makes MeshLink easiest to use?](issues/15-public-api-shape.md): one `MeshLink` per process with `StateFlow` state and peers, a typed `Blocked` state for missing permissions or Bluetooth, and non-suspend `send` and `broadcast` returning sealed results with a per-message `DeliveryStatus`. Messages wait in a bounded, fair-share inbox for one collector. Config is one DSL with sealed presets (custom allowed); the security profile is required, and `none` is renamed `unsecured`. Expected failures are values; Flows never throw. Swift uses SKIE plus a thin overlay; a `meshlink-testing` fake mesh ships separately. Prototype passes in Kotlin and Swift. Recorded in ADR 0007.
- [Which BLE bearer(s) and PHY policy should MeshLink use?](issues/12-bearer-phy-bakeoff.md): GATT first, then an upgrade to unbonded L2CAP CoC with fallback (on by default); connect with 1M|2M, then prefer 2M; 3 connect retries for 133/147 and a keep-one rule for crossed links; iPhones accept at most 3 incoming links. Android 10+ and iOS 15+ fully supported, Android 8/9 GATT only. Measured on real devices; recorded in ADR 0009.
- [How do nodes discover each other, and what goes in the advertisement?](issues/13-discovery-advertising.md): a legacy 1M advertisement with a fixed 32-bit `MESH` UUID plus one rotating 128-bit UUID (mesh tag, resolvable tag, flags). Identifiers and routing tags rotate every 5 min; Android restarts its advertising set so the address changes too, while iOS rotations stay linkable. Gated meshes recognize linked peers through daily resolving keys. Backgrounded iPhones show only an overflow bit, so MeshLink connects to read the identifier; Live Activity is an opt-in hook. Measured on real devices; recorded in ADR 0010.
- [What is the wire format, and which codec implements it?](issues/18-wire-format-codec.md): a hand-written codec; Kompact was safe on every input but 2–8× slower, and bit-packing saved only 1–2 B per frame. Frames are byte-aligned and big-endian; each bearer is one ordered stream of length-prefixed records; fragments are link-local (3 B header). A protocol version byte in the capability read and the Noise prologue; extensions as handshake TLVs. Absolute 4 B expiry, 32 B NodeId, fixed-layout certificate, 16 B advertisement with one bit-packed byte, 32 B padding in secured profiles. Measured on the JVM, two Android phones and an iPhone; recorded in ADR 0012.
- [How are modules cut, and how do feature toggles and presets work?](issues/17-modules-toggles-presets.md): one published `meshlink` artifact (libsodium included) plus `meshlink-testing`, and one umbrella XCFramework; internally `:meshlink-core`, `:meshlink-crypto-sodium`, `:meshlink` and `:meshlink-testing`. `Package.swift`, the Swift overlay and a pure Swift fake live in a separate `meshlink-swift` repository. Toggles govern only local origination, holding and radio use, never relaying; no relay-off mode. Presets are named defaults overridden by the DSL; the draft matrix waits on receipts, store-and-forward, size and power. Recorded in ADR 0011.
- [Which routing and topology strategy should MeshLink use?](issues/14-routing-topology-simulation.md): HyParView-style views with a diversity preference (d = 6/5/5, bridge rule, iOS incoming links ≤ 3). Each node estimates its own local density and adapts locally: flooding at low density; U6 unicast with ack-refreshed routes and Plumtree broadcast with catch-up at medium and high. The wire format is the same everywhere. Minimum lifetime is 120 s, the routing tag 8 B, the message ID 12 B, with 5 min rotation (amended from 15 by ADR 0010). All simulated. Recorded in ADR 0008.
- [Which crypto options fit each security profile?](issues/03-crypto-options.md): no secured profile can rely on platform crypto alone at Android 26 / iOS 15. Classical fits standard Noise (XX, then IK/KK; every message <100 B). Post-quantum means hybrid X25519 + ML-KEM-768 with classical authentication, via Noise hfs (~2.4 KB) or a cairn-style pairing plus a 106 B resume, and always needs fragmentation. Candidate providers: libsodium, Rust aws-lc-rs, or a platform split.
- [Which routing and topology strategies suit phone BLE meshes?](issues/04-routing-topology-strategies.md): with only 3–6 links per phone, neighbor selection matters as much as routing, and mesh-wide flooding won't scale to ~1,000 nodes without a hop limit. The simulation shortlist covers neighbor selection, unicast, broadcast and store-and-forward strategies.
- [Are Swift interop and libsodium fast enough on the iPhone SE (2016)?](issues/24-se2016-interop-crypto-bench.md): yes; post-quantum handshake crypto under 0.8 ms per side and a Swift round trip about 0.1 ms on the slowest iPhone. A sender retrying `QueueFull` in a loop overwhelmed the garbage collector, so `send` gains `awaitSendCapacity()` (ADR 0007 v3); the overlay bulk-copies `Data`; libsodium symbols get an export allow-list and a CI gate (ADR 0004 v2).
- [What are the message lifecycle and receipt semantics?](issues/19-message-lifecycle-receipts.md): the routing ack is the always-on delivery receipt; read receipts need sender request and recipient permission, carry no timestamp and are best effort; broadcasts get no receipts. Statuses only move forward, `Failed` is local-only, `Expired` at expiry plus 30 s; status is in memory. ADR 0013.
- [How does store-and-forward work?](issues/20-store-and-forward.md): short-term only (lifetime at most 1 h). The origin keeps its copy and relays hold best-effort copies in memory (100 messages, ¼ per link); broadcasts are held too; catch-up offers held messages; delivered copies are purged by tombstones only the destination can produce. Certificates valid 24 h, renewed every 12 h; residual tracking bounded at 1 h. ADR 0014.
- [What is the message size cap, and is there compression?](issues/21-message-size-compression.md): small unicast (≤4 KiB) behaves as before; large unicast up to 128 KiB (profile pictures) is never flooded, goes only over a direct link or a discovered route, and is held only by its origin. Broadcasts 1 KiB; no compression; 1,024 B records; bounded reassembly with a link-local busy reply. ADR 0015.
- [What does MeshLink cost in energy on real phones?](issues/23-energy-on-devices.md): on the Pixel 6 Bluetooth rail, scanning costs about 55 mW × scan duty, advertising is unmeasurable, an idle link about 1 mW, a relayed message 0.25 mJ, bulk 0.75–0.83 mJ/KiB; overnight with Doze about 8 mW. This absolute model replaces the power index. No continuous scans: start/stop windows of at least 6 s (interim 4/4 for low and medium, 4/8 for high). iOS is reported as bounds, and its overnight background cost is below night-to-night variation; the OS owns background duty on both platforms. Power policy moves to [ticket 33](issues/33-power-policy.md); re-measurements to tickets [34](issues/34-energy-second-android.md) and [35](issues/35-ios-power-profiler.md). ADR 0008 v6, ADR 0010 v3.
- [What does MeshLink cost on iOS when measured with Apple's Power Profiler?](issues/35-ios-power-profiler.md): on the iPhone 12 mini, screen on, foreground medium discovery costs about 5–80 mW of whole-phone power; background discovery is not resolvable (median about 0, at most about +17 mW). Sending an app to the Home screen alone costs about 53 mW, so background comparisons need a Home-screen idle control. ADR 0008 v10, ADR 0010 v5.
- [How do open and unsecured meshes resist fake identities (Sybil)?](issues/22-sybil-resistance.md): they don't, at the routing layer. In simulation, peer scoring, probation slots and confirmed neighbor lists all left the honest mesh split at 30% fakes, because free identities refill freed slots; smart fakes black-hole unicast while relaying broadcasts. Proof of work rejected. 3 attacker radios barely matter: the real cost is radios. Gated meshes are the availability answer. ADR 0008 v7.
- [What do members learn about neighbors and routes?](issues/25-neighbor-list-privacy.md): direct neighbors learn your identity (XX), your other neighbors' on-air identifiers and your recent catch-up summary. Public routing tags now derive from the certified static key (recognizable ≤ ~25 h); after the first message, conversations use tags only the two ends can compute, so relays see only "someone contacted D". Neighbor lists carry advertisement identifiers to direct neighbors only. Hop counts, timing and broadcast origin are documented, not hidden. ADR 0016; ticket 32 checks the per-conversation route cost.
- [What is the testing architecture?](issues/26-testing-architecture.md): a sans-IO core, tested deterministically. One seeded `VirtualAir` in `meshlink-testing` serves both MeshLink's own multi-node tests (2–12 nodes per PR, 50–200 scheduled) and apps' tests. Real libsodium runs in host tests. Robolectric covers only the Android adapter; iOS runs on the simulator, with thin CoreBluetooth calls checked on devices. Fuzzing has two tiers: a deterministic test per PR and scheduled Jazzer. One vector runner. Devices are run by hand through `tools/lab/` before releases, covering all pairs, both roles, and the oldest and newest OS. No retries; a flaky test is a bug. ADR 0017.
- [How does a sender obtain the certificate of a node it has never linked with?](issues/31-certificate-acquisition.md): apps send to a NodeId and MeshLink gets the certificate. It checks its own cache first (links, `IK` senders, refreshes), then runs a salted, anonymous lookup. D or any node caching its certificate answers, sealed to the requester's ephemeral key, so relays don't learn it and an offline D can still receive held first messages. The message stays `Queued` meanwhile; `PeerKeyExpired` is gone. Lookups reveal "someone is looking for D" to NodeId holders. Cost goes to ticket 32. ADR 0018.
- [What is the release, versioning and API-compatibility process?](issues/27-release-versioning.md): one SemVer version for all artifacts, starting at 0.1.0. The protocol byte is versioned independently, and a new protocol major also speaks the old one for one MINOR. Kotlin ABI dumps with explicit API, `swift-api-digester` for Swift, and a hand-written changelog enforced on dump changes. A tag starts the gates, the device evidence check and manual approval, then Maven Central, an attested XCFramework, Pages, the `meshlink-swift` update through a GitHub App, and consumer smoke tests. ADR 0019.
- [What is the diagnostics code catalog?](issues/28-diagnostics-catalog.md): 40 stable `MLnnnn` codes in ranges by area, never reused, add-only after 0.1.0, with Debug opt-in. Peers appear only as a per-start keyed `PeerRef`; tags, advertisement identifiers, keys and payloads never appear in events. Repeats are coalesced and the buffer holds 256 events. A redacted snapshot with counters, a JSON export the app owns (never uploaded), and opt-in Logcat/`os_log` output for the lab. ADR 0020.
- [Does catch-up of held messages and tombstones fit the airtime budget?](issues/32-catch-up-airtime-simulation.md): yes, simulated (stage F). Full catch-up, per-conversation routes, certificate lookups and large messages fit, once relays pass on only the first lookup reply. Two criteria were amended after the results: an absolute busiest-phone budget and a minimum sample of 100 messages. No route-request rate limit. ADRs 0008, 0014, 0015, 0016, 0018 amended.
- [What power policy should each preset and density class use?](issues/33-power-policy.md): `Balanced` scans low 4/4, medium 4/12, high 4/16 (seconds on / off); `Responsive` is one step faster, used by `ProximityDiscovery` and `LocalMultiplayer`. Low scans more because newcomers start in the low class. `Balanced` uses 17–22 mW in dynamic scenarios, down from 24–34 mW. ADRs 0008, 0011 amended.
- [Write the v1 protocol spec](issues/29-protocol-spec-v1.md): protocol 1 is a Draft spec in `docs/spec/` (identity, discovery, link, routing, end-to-end). JSON data files are the authority, checked against the tables by `tools/spec/check_spec.py`. 43 accepted byte-level and numeric decisions sit in a decision log. 10 ADR conflicts are resolved by amending ADRs 0002, 0009, 0010, 0012, 0014, 0015 and 0018 (rotation is 5 min everywhere; `NEIGHBOR_LIST` carries the next identifier). There are 253 tier-1 vectors (layouts, hash derivations); crypto vectors wait for the Kotlin and Rust implementations to agree, before 1.0.0.
- [Create the GitHub repositories and first workflows](issues/30-github-repositories.md): `trancee/MeshLink` is public; history was scrubbed of device serials, UDIDs, team IDs, LAN addresses, home paths and email before the first push, and `tools/check_private.py` guards it in CI. `main` has a ruleset against force-push and deletion; rebase merges only; private vulnerability reporting on. Release infrastructure split to [ticket 36](issues/36-release-infrastructure.md).

## Out of scope

- Post-quantum signatures in v1: ruled out by the [threat model](issues/08-threat-model.md). Signatures stay classical (Ed25519); SQIsign is the leading candidate for a later suite version once NIST standardizes it.
- Encrypted named groups (group key agreement, e.g. MLS).
- File transfer and streaming: profile pictures up to 128 KiB are messages (ADR 0015); resumable transfers, larger payloads and progress APIs are not.
- Targets other than Android and iOS.
- Wire compatibility with Bluetooth SIG Mesh, bitchat, Briar or other meshes.
- Multi-device users and account sync.
- Non-BLE bearers (Wi-Fi Aware, Multipeer Connectivity, Nearby Connections): v1 is BLE-only; the bearer abstraction of ADR 0009 keeps a later addition possible (user decision 2026-11-02).
- Precise distance via UWB (Nearby Interaction, Android UWB): possible later optional module; v1 offers only coarse proximity for direct peers.
- [Does the energy model hold on a second rail-equipped Android phone?](issues/34-energy-second-android.md): needs a Pixel 7 or newer, which the lab lacks; the spec does not depend on it. Carried forward.
- [Set up the release infrastructure](issues/36-release-infrastructure.md): execution work, blocked on 0.1.0 code. Carried forward.

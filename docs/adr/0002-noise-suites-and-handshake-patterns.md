# 0002: Noise suites and handshake patterns per security profile

Status: accepted (2026-10-31; ticket "What handshake and crypto suite does each security profile use?"). Version: 3 (amended 2026-11-01, libp2p alignment; 2026-11-08, protocol spec).

Terminology note (2026-11-01, ADR 0007): the profile written `none` here is named `unsecured` everywhere else, because Swift's `.none` collides with `Optional.none`. Meaning unchanged.

## Context

[ADR 0001](0001-threat-model-and-profile-guarantees.md) fixes what each security profile guarantees: authenticated, encrypted links plus end-to-end encryption in the secured profiles, open or mesh-key-gated admission, rotating on-air identifiers, and hybrid confidentiality with classical authentication for `post-quantum`. No platform provider covers both secured profiles at Android 26 / iOS 15, and Xcode 16.4 (iOS 18.5 SDK) rules out CryptoKit ML-KEM/X-Wing, so crypto is bundled. Rule S6 requires established constructions and S7 requires conformance vectors.

## Decision

- **One framework.** Both secured profiles use the Noise Protocol Framework: one handshake state machine, one transport. Each profile has exactly one suite per protocol version, never negotiated. `none` uses no Noise.
- **Primitives.** No FIPS-only requirement. X25519, ChaCha20-Poly1305 and SHA-256: ChaChaPoly is constant-time in software on every supported phone; SHA-256 has the widest vector coverage.
- **Link layer: XX only.** `Noise_XX_25519_ChaChaPoly_SHA256`; in a gated mesh, `XXpsk3` with psk = HKDF-SHA-256 of the mesh key bound to the mesh identifier. A node cannot know its peer before the handshake, because on-air identifiers rotate, so patterns that need the peer's static key in advance (IK, KK) are unusable for links.
- **Post-quantum link layer.** The same patterns with Noise's `hfs` extension and ML-KEM-768 (`XXhfs`, `XXhfspsk3`): about 2.5 KB per link establishment.
- **End-to-end layer: IK.** The sender knows the destination's identity certificate. The first message rides as the 0-RTT payload of IK message 1 (no forward secrecy). Later messages, after the destination's reply, have forward secrecy. Store-and-forward carries IK message 1. In `post-quantum` the pattern is `IKhfs`.
- **Post-quantum first and held messages.** In `post-quantum`, the 0-RTT payload is first sealed with HPKE using the X-Wing KEM to the destination's certified X-Wing static key, then carried inside `IKhfs` message 1. Nesting keeps it confidential if either layer holds, so harvest-now-decrypt-later protection covers first and held messages without a new combined construction. Cost: +1,120 B per first or held message, plus a one-time 1,216 B key in the certificate. No extra round trip.
- **Sessions.** A fresh XX handshake on every new link connection, with no resumption; Noise `Rekey` on a time and message-count schedule while connected. End-to-end IK sessions have a maximum age and message count and live in a bounded LRU cache sized per preset. The spec fixes the numbers after simulation and bake-off calibration.
- **Handshake denial-of-service bounds.** Per-link and global caps on half-open handshakes, a handshake timeout, per-neighbor handshake rate limits, and handshake reassembly capped at the largest legal handshake message. Violations are dropped with typed diagnostics.
- **Conformance vectors.** Wycheproof for X25519, Ed25519, ChaCha20-Poly1305, HKDF and ML-KEM-768; cacophony for XX, XXpsk3 and IK. MeshLink's own vectors for `XXhfs`, `XXhfspsk3`, `IKhfs`, the identity certificate and the nested X-Wing seal: generated by two independent implementations that must agree, and published with the protocol spec (C10).
- **Latency safeguard.** First-message latency, classical versus post-quantum by hop count and density class, is an explicit metric in the routing simulation and the device-lab bake-off. Exceeding a budget the project owner sets returns the trade-off to them.

## Alternatives

- FIPS-approved only: rejected; no requirement, and it would exclude ChaChaPoly and X25519-primary key exchange.
- AES-GCM: rejected; the bundled libsodium AES-GCM needs ARM crypto extensions, and software AES is not constant-time.
- IK or KK for links: impossible without advertising identity.
- `XXpsk0`: rejects non-members one message earlier but has no standalone vectors. Gated on-air identifiers already hide the mesh from non-members.
- cairn-style pay-once X-Wing pairing plus resume: smallest steady-state airtime, but a novel composition (spec, formal model, expert review), and its per-peer resume ticket is linkable. Revisit if link churn makes `XXhfs` too costly.
- PQNoise (KEM-only): about 6.9 KB per handshake.
- One-shot `X`/`K` per end-to-end message: no forward secrecy at all.
- No 0-RTT in `post-quantum`: makes store-and-forward to offline recipients impossible.
- Classical-only first and held messages in `post-quantum`: weakens ADR 0001 exactly where exposure is highest.

## Risks

- `hfs` is an unofficial Noise extension with no public vectors. Mitigated by two-implementation vectors and expert review before release.
- HPKE with X-Wing: standardization status and provider support are unverified; the crypto-provider ticket verifies them.
- Post-quantum first messages are about 2.3 KB larger than classical. Modeled at roughly 13–24 ms per hop on ideal radio, or 45–230 ms per hop at an illustrative 10–50 KB/s; unmeasured. Mitigated by the latency safeguard.
- `XXhfs` costs about 2.5 KB per link establishment, which may be high under link churn at high density. The simulation and bake-off measure it.

## Migration

None: greenfield. A suite change is a new protocol version with new vectors (C6, C7, C10).

## Amendments

2026-11-01, libp2p alignment (user decision: study only, plus aligned `XXhfs`):

- **Context:** libp2p's Noise spec uses the same suite and identity model. Its open post-quantum proposal ([specs#723](https://github.com/libp2p/specs/issues/723), [#727](https://github.com/libp2p/specs/pull/727)) is `Noise_XXhfs_25519+ML-KEM-768_ChaChaPoly_SHA256`, with token placement and KDF order taken from the Noise HFS spec.
- **Decision:**
  - MeshLink's `XXhfs` handshake is byte-compatible with that proposal at the Noise layer: the same protocol name string, the same `e1`/`ekem1` token placement, the same mixing order.
  - MeshLink's handshake payload and protocol identifier stay its own. There is no libp2p payload compatibility and no libp2p stack.
  - Vectors are cross-checked against snow with ML-KEM-768 `hfs` ([snow#210](https://github.com/mcginty/snow/pull/210), once merged, or a pinned commit if approved) and any vectors libp2p publishes.
  - If the libp2p proposal diverges from the Noise HFS spec, the HFS spec wins and the divergence goes back to the project owner.
- **Status:** the libp2p proposal and snow#210 are open as of 2026-11-01.

2026-11-08, protocol spec ([ticket 29 decision log](../spec/decisions.md)):

- **Post-quantum seal overhead ([C-06](../spec/decisions.md#c-06)):** the nested HPKE X-Wing seal adds 1,136 B, not 1,120 B: the 1,120 B X-Wing encapsulation plus the 16 B HPKE AEAD tag. `IKhfs` adds its ML-KEM fields on top of `IK`.
- **Numbers left to the spec:** rekey every 3,600 s or 65,536 records ([D-21](../spec/decisions.md#d-21-rekey-schedule)); end-to-end sessions last 6 h or 4,096 frames per direction with an explicit 64-bit nonce and a 1,024-nonce replay window ([D-33](../spec/decisions.md#d-33-end-to-end-session-limits)); handshake bounds of 4,096 B per Noise message, one handshake per bearer, 8 at once, a 10 s timeout and one new handshake per remote address per 2 s ([D-20](../spec/decisions.md#d-20-handshake-denial-of-service-bounds)); HPKE base mode with KEM 0x647A, HKDF-SHA256 and ChaCha20Poly1305 ([D-35](../spec/decisions.md#d-35-hpke-parameters)).

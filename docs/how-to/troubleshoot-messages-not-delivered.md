# Troubleshoot messages that aren't delivered

Use this guide when `send()` returns but the recipient never gets the message, the receipt never arrives, or the message arrives late. If the recipient isn't in `MeshLink.peers` at all, start with [Troubleshoot peers that aren't found](troubleshoot-peers-not-found.md).

## Collect the evidence

1. Turn on [`diagnostics.debug`](../reference/configuration.md#diagnosticsdebug) in the configuration, so `meshLink.diagnostics.events` also emits the `Debug` events.
2. Collect `meshLink.diagnostics.events` on the sender, the recipient and, if you can, a phone between them, and send again.
3. Take `meshLink.diagnostics.snapshot()` on each. Its `queues` shows the messages waiting to send, the frames held for absent peers and the messages waiting in the inbox.

## Check the recipient collects its messages

If the recipient reports [`ML7003`](../reference/diagnostics.md#ml7003) (inbox full), or its snapshot's `queues.inbox` keeps growing, the app doesn't collect `meshLink.messages`, or collects it slowly. Collect it for as long as the node runs.

## Check the route to the recipient

If the sender reports [`ML5002`](../reference/diagnostics.md#ml5002) (route lost) or [`ML6003`](../reference/diagnostics.md#ml6003) (certificate lookup unanswered), the recipient moved out of reach of the mesh or stopped. Bring the phones closer together, or send again once the recipient is listed in `MeshLink.peers`.

If [`ML3002`](../reference/diagnostics.md#ml3002) (link closed) repeats with `reason=ProtocolError`, the peers run incompatible MeshLink versions, or a record was corrupted. Update both apps to the same MeshLink version.

## Check the clocks

If any phone reports [`ML5004`](../reference/diagnostics.md#ml5004) (expiry far from local time), it dropped a routed message because the sender's clock and its own differ too far; `skewSeconds` tells by how much. Set every phone of the mesh to the network-provided time.

## Send less at once

If you see [`ML3009`](../reference/diagnostics.md#ml3009) (busy reply), [`ML7004`](../reference/diagnostics.md#ml7004) (reassembly budget exhausted) or [`ML6001`](../reference/diagnostics.md#ml6001) (held message evicted), the mesh carries more than it can hold. The senders retry, but a phone that comes back later may miss evicted messages. Send fewer large messages at once, and fewer messages to absent peers.

If you see [`ML7002`](../reference/diagnostics.md#ml7002) (read tracking evicted), request read receipts only for messages whose reading matters.

## When messages arrive late

If messages arrive but slowly, look for [`ML3005`](../reference/diagnostics.md#ml3005) (bearer fallback): the link stays on GATT, which is slower than an L2CAP channel. Look also for [`ML3006`](../reference/diagnostics.md#ml3006) (GATT operation retried): another app or the stack holds the phone's GATT queue. If it repeats, close other Bluetooth apps on the phone.

## If the problem stays

Open an issue with `meshLink.diagnostics.export()` from the sender and the recipient attached. The export holds no key, payload, NodeId, mesh ID or Bluetooth address ([Diagnostics export](../reference/diagnostics-export.md)).
